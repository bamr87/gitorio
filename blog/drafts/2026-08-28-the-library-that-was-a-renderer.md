## The ask, and the premise check

The request was blunt: refactor, rebuild, redesign, and reconfigure the whole repo to use `tt-a1i/archify` as the main UI/UX library. Before planning a word of it we fetched the repo — README, SKILL.md, DESIGN.md, PRODUCT.md, the schemas — and the premise fell over. Archify is a Node CLI plus an agent skill (24k stars, MIT, `v2.16.0-dev`, no npm package) that compiles a typed JSON IR — architecture, workflow, sequence, dataflow, lifecycle — into one self-contained interactive HTML/SVG map with search, focus, route tracing, reach analysis, guided views, presentation mode, and exports. It ships no components. It has no editing model; its own PRODUCT.md says it is "not a general-purpose drawing editor". Its renderers run at module scope over `process.argv` and `node:fs`, so they cannot run inside a static frontend at all.

So "swap React for archify" was never on the table. What archify actually offers GitFactory is three things: a design system (DESIGN.md — "The Evidence Console"), a renderer for every read-only map we have been drawing badly with a second React Flow canvas, and a skill agents can use. We wrote that down as ADR-034 and planned around it.

## What shipped: specs/010-archify-maps

Archify is vendored at a pinned commit under `vendor/archify/` (2.1 MB, renders and validates with no `npm install`, byte-deterministic across runs). Beside the compiler there is now a second pure consumer of the data model, `app/src/archify/ir.ts`:

- `toWorkflowIR(blueprint, line)` compiles one assembly line — from the same `assemblyLines()` partition that names the emitted `factory--*.yml` — into a workflow diagram. Lanes are roles (Triggers → Gates & limits → Processing → Outputs), columns follow topological depth, and `mainPath` is the longest trigger→sink walk.
- `toArchitectureIR(fleet)` compiles a reverse-imported fleet into an architecture diagram: one boundary per repo, workflows ranked so the agent-bearing and belted ones survive a 12-component budget, the rest collapsed into "N more workflows".
- `vocabulary.ts` fixes what each of the 27 machine kinds *means* in archify's seven semantic colours, with a drift guard against the registry.

`npm run maps` renders the eight dogfood + demo maps into `app/public/maps/` with a `GENERATED BY GITFACTORY` header on line 2, the Google Fonts link stripped so Pages serves them offline, and `archify check` + showcase validation on the result. `npm run maps:check` diffs a fresh render against the committed files; a CI `diagram-gate` job runs it. 20 new tests spawn the vendored CLI at showcase quality over both dogfood blueprints and the three demo repos — a green test means a rendered map.

## The gnarly bit: archify's composition rules are opinionated, and that is the point

The workflow renderer has six columns at fixed x positions (`88, 220, 300, 430, 500, 625`) and a 92 px node, so two nodes in the same lane need at least 100 px between them — columns 1 and 2 are only 80 px apart. A naive "column = depth" placed the Dependency Warden's three sinks on top of each other. The first fix, a collision resolver that also searched leftward, produced a backward belt that archify's `clean-flow` rules rejected. The second, an overflow lane, produced belts crossing an unrelated lane — `edge-through-node`, rejected again.

The fix that survived is the honest one: placement is rightward only, and when a lane is full the tail collapses into one "+N more" node with the collapsed kinds in its sublabel, exactly the device the fleet map uses. Every rejection archify raised was a real readability defect; fighting the validator would have meant shipping a worse map.

One more truth-preserving detail: whenever a line is loop-prone by ADR-009's condition (an event trigger an agent's own write can re-emit, plus a writing sink), the map draws the compiler's bot-actor guard as a node in an exception lane. The YAML carries that guard; now the picture does too.

## What is deliberately not here

Decision D-1 — pre-rendered only — has a consequence the plan under-weighted: the app can only show maps that exist as files, which today means gitorio's own lines and the demo fleet. A "Map" button in the Build tab for an arbitrary blueprint being edited in the browser has nothing to render until either the Cartographer line (regenerate on push, filed as a follow-up) or a fork of the renderers exists. The in-app Map surfaces and the design-token migration are therefore separate companion specs, sequenced after this one, rather than half-built here.

## Working-with-AI tip

Verify the premise before you plan against it. The user's request named a library and a role for it; one `WebFetch` of the README and a `git clone` into the scratchpad showed the role was wrong before any code was written, and the plan opened with that correction rather than burying it. The same habit paid off three more times in the session: reading the renderer's column constants instead of guessing lane capacity, testing that a header comment on line 2 survives `archify check` before wiring it into the generator, and spawning the real vendored CLI in the tests instead of re-implementing its rules. When the tool you are integrating has a validator, make the validator the test.
