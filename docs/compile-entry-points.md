# Compile entry points and the expected-equivalence contract

> **Status: draft.** This document was assembled from the repository README and
> the top-level file listing. Sections marked **⚠️ Unverified** have *not* been
> confirmed against the compiler source or the test suite and must be checked by
> a maintainer before this document is treated as normative. Nothing below
> should be cited as a guarantee until its marker is removed.

## 1. Why this document exists

GitFactory compiles a blueprint into artifacts that are **committed to the
repository** — the generated workflows under `.github/workflows/factory--*.yml`
carry a `GENERATED BY GITFACTORY` header and are never hand-edited, and
`examples/compiled/` holds "reference output the compiler converges to"
(README, *Repository layout*).

Committed output means a compile can be invoked from more than one place, and
those places must agree. If the in-app compile and the test-time compile
disagree by even a byte, the repository develops drift that shows up as noisy,
unreviewable diffs — and reviewers stop trusting the `GENERATED BY GITFACTORY`
header, which is the whole point of the compile-to-Actions design.

This document is the single place that answers three questions:

1. **Where can a compile be invoked from?** (§2)
2. **Which outputs must be identical across those entry points?** (§3–§4)
3. **Which differences are tolerated, and why?** (§5 — the exception list)

A differential test that runs the entry points over the same input and compares
their output should normalise against §5 and nothing else. If a difference is
not in §5, the difference is a bug, not a fact of life.

## 2. Entry points

An *entry point* is any code path that turns a blueprint (or blueprint-derived
IR) into an artifact a human or a machine will later read.

| # | Entry point | Input | Output | Evidence |
| --- | --- | --- | --- | --- |
| **E1** | **In-app Compile** — the canvas's Compile action in the static frontend | The blueprint currently on the canvas | Generated workflow YAML shown in the app | README, *Quickstart*: "press **Compile** to see the generated workflows" |
| **E2** | **Test-time compile** — the vitest suite (`npm test`) | Blueprints under `examples/` | Compared against `examples/compiled/` | README, *Quickstart*: `npm test  # vitest — compiler invariant tests`; *Repository layout*: `examples/` holds "Example blueprints and `compiled/` reference output the compiler converges to" |
| **E3** | **Fleet-lane compile** — `toFleetLanes` | The blueprint's assembly lines | `fleet/v1` lanes, pinned against `fleet.manifest.yml` by a parity test | README, *Repository layout*: "GitFactory compiles the same lanes from the blueprint (`toFleetLanes`) and a parity test pins them to this file" |
| **E4** | **archify IR compile** — `app/src/archify/` feeding the in-app map surface `app/src/map/` | Assembly lines | archify map rendering (lanes as roles, main path, bot guard) | README, *The console* |
| **E5** | ⚠️ **Unverified** — whatever regenerates the committed `.github/workflows/factory--*.yml` files | `.factory/blueprint.json` | Committed workflow YAML | README names hand-written "CI/Pages/**evolve**" workflows alongside the compiled `factory--*.yml` files, but the regeneration mechanism was not inspected. **Fill in or delete this row.** |
| **E6** | ⚠️ **Unverified** — a headless/CLI compile, if one exists | — | — | The README documents no npm script other than `dev`, `test`, `typecheck`, `lint`, `build`. If no CLI compile exists, **delete this row** and say so, because "there is deliberately no CLI" is itself useful information. |

### Entry points that are *not* in scope

- The **Docker** commands (`docker compose run --rm dev npm test`, etc.) are not
  separate entry points: the README states they "run the same npm scripts inside
  a container". They are E2/E5 under a different execution environment. They are
  nonetheless a legitimate *environment* axis for the differential test — see
  §5's open question on line endings and locale.
- The **VS Code launch configs** (`.vscode/launch.json`) likewise invoke the
  existing npm scripts under a debugger.

## 3. The equivalence contract

> **Contract (proposed).** For a fixed blueprint, a fixed
> `schema/blueprint.schema.json`, and a fixed machine registry, every entry
> point that emits workflow YAML MUST emit **byte-identical** output, modulo
> the ratified exceptions in §5.

Unpacking the three parts:

**"For a fixed blueprint …"** — the contract holds per-input. Two different
blueprints are expected to compile differently; that is not drift. The
differential test therefore compares *the same input across entry points*, never
different inputs against each other.

**"… and a fixed schema and machine registry …"** — the schema is
"drift-guarded against the machine registry" (README, *Repository layout*), so
the schema and the registry move together. Output may legitimately change when
*they* change; that is a versioned change, reviewed on its own merits, not an
equivalence violation. A regenerated `examples/compiled/` in the same commit as
a registry change is expected.

**"… MUST emit byte-identical output."** Byte-identical, not
semantically-equivalent. Semantic equivalence is unfalsifiable in review: a
human reading a diff cannot tell whether reordered keys change behaviour. Byte
equality is checkable by a machine, so that is the bar. Where byte equality is
genuinely impossible, the difference goes in §5 with a rationale — it does not
get waved through as "semantically the same".

### 3.1 Which outputs the contract covers

| Output | Covered? | Note |
| --- | --- | --- |
| Generated workflow YAML (`factory--*.yml`) | **Yes** — this is the primary artifact | It is committed and carries the `GENERATED BY GITFACTORY` header |
| `examples/compiled/` reference output | **Yes** | It is the fixture the contract is measured against |
| `fleet/v1` lanes vs. `fleet.manifest.yml` | **Yes, with a stated carve-out** | The README notes "hand edits survive" in `fleet.manifest.yml`, so lane parity is asserted over the compiled lanes, not over the whole file. ⚠️ **Unverified** — confirm exactly which keys the parity test compares. |
| archify maps rendered in-app (E4) | ⚠️ **Unverified** | Whether the in-app map must match the delivered HTML maps under `app/public/maps/` byte-for-byte, or only structurally, is not established here. The README calls the delivered maps "the canonical, exportable artifacts", which suggests they are the source of truth rather than a compile target. |

## 4. Why the contract is worth enforcing

Three failure modes it prevents:

1. **Silent divergence between what you see and what you ship.** If E1 (what the
   canvas shows on Compile) drifts from E5 (what lands in
   `.github/workflows/`), the app becomes a plausible-looking preview of
   something else. The preview is the product's main claim; drift falsifies it.
2. **Unreviewable regeneration diffs.** Generated files are only auditable if a
   regeneration with no input change produces a no-op diff. Any unratified
   per-run variation (timestamps, ordering, versions) destroys that property.
3. **Exceptions accumulating as folklore.** Without a written list, each
   tolerated difference lives in one test's normalisation helper and in one
   person's memory. §5 makes the set finite, named, and reviewable.

## 5. Normalisation exceptions

**Ratified exceptions: none recorded.**

This is deliberately empty rather than pre-populated with guesses. An entry here
is a promise that a difference is *acceptable forever*, and that promise should
only be made by someone who has read the code producing it.

### 5.1 Required format

Every exception is one row. All columns are mandatory; a row without a rationale
is not an exception, it is an unfixed bug.

| ID | Applies to | What differs | Normalisation rule | Rationale (why it cannot be made identical) | Ratified in |
| --- | --- | --- | --- | --- | --- |
| `NX-000` | *(example row — not a real exception)* | — | — | — | — |

- **ID** — stable `NX-NNN`, never reused, so tests and review comments can cite it.
- **Applies to** — which entry points and which artifact. An exception scoped to
  one pair of entry points must not be applied globally.
- **What differs** — the precise field, key, or line pattern.
- **Normalisation rule** — the exact transform the differential test applies
  before comparing. Must be mechanical and stated tightly enough that someone
  could reimplement it.
- **Rationale** — *why* byte-equality is unachievable or undesirable here. "It's
  annoying to fix" is not a rationale.
- **Ratified in** — the PR that added the row.

### 5.2 Adding an exception

1. Try to remove the difference first. Most candidate exceptions (ordering,
   whitespace) are cheaper to eliminate at the source than to normalise forever.
2. If it cannot be removed, open a PR that adds the row **and** the matching
   normalisation in the differential test in the same change, so the list and
   the code cannot drift apart.
3. Scope it as narrowly as the rule allows. A regex that swallows a whole header
   block will hide the next real regression in that block.

### 5.3 Removing an exception

Exceptions are debt. If the underlying cause is fixed, delete the row and its
normalisation in the same PR. Do not leave dead normalisations behind — a
normalisation nobody needs is a permanently blind spot in the test.

### 5.4 Open questions for the first ratification pass

These are **questions, not exceptions**. None is asserted to be a real
difference; each needs someone to check the compiler and either answer "no
difference exists" or file a row in §5.1.

- **Generator header.** Compiled workflows carry a `GENERATED BY GITFACTORY`
  header (README). Does that header include anything per-run — a version, a
  timestamp, a source hash? If so, is it stable across entry points?
- **Key and lane ordering.** Is the emission order of workflow keys, jobs, and
  compiled lanes fully deterministic from the blueprint, or does it depend on
  iteration order of a map/set that could differ between the browser (E1) and
  Node (E2)?
- **Line endings and trailing newline.** `.gitattributes` and `.editorconfig`
  exist at the repository root; confirm whether either normalises the generated
  YAML, and whether a compile run inside the Docker `dev` container agrees with
  a compile run on a host.
- **YAML serialiser settings.** Quoting style, indentation, and line-folding are
  serialiser-configuration-dependent. Do all entry points share one serialiser
  configuration, or does each construct its own?
- **`fleet.manifest.yml` hand edits.** The README states hand edits survive.
  Which keys are therefore outside the parity assertion, and is that carve-out an
  exception under §5 or a scoping rule under §3.1?

## 7. Maintenance

This document is only useful if it is true. When an entry point is added,
removed, or renamed, update §2 in the same PR. When the differential test's
normalisation changes, update §5 in the same PR. If the two ever disagree,
**the test is authoritative and this document is the bug.**
