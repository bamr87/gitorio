# Blueprint → compiled output

> **You probably arrived here from a banner** at the top of a generated file. The
> short answer: that file was written by the compiler, your edit will be
> overwritten, and the thing you actually want to change lives in `.factory/`.

This page is the contributor-facing map of the one-way road from a blueprint to
the GitHub Actions workflows it produces. For the authoritative list of exactly
which files the compiler writes, plus the determinism and action-pinning
guarantees it makes, see [`GENERATED-FILES.md`](GENERATED-FILES.md).

## The one-way rule

**Source is edited. Output is regenerated. Never the reverse.**

GitFactory compiles a blueprint into readable GitHub Actions YAML. The emitted
YAML is designed to be auditable and to keep working without GitFactory
existing — which is exactly why it is tempting to "just fix it in place". Don't.
The next compile will discard your change, and the drift check will fail in CI
before that even happens.

If a generated workflow is wrong, one of these is the real defect:

| Symptom | Fix it here |
| --- | --- |
| Wrong machines, wiring, or triggers | `.factory/blueprint.json` |
| An agent behaves badly / prompt is stale | `.factory/prompts/*.md` |
| Repo-level compile settings | `.factory/config.yml` |
| The *shape* of the emitted YAML is wrong for every blueprint | the compiler, `app/src/compiler/` |
| A blueprint field isn't accepted | `schema/blueprint.schema.json` (+ the machine registry it is drift-guarded against) |

## Source vs. generated, by directory

### Source — edit these

| Path | What it is |
| --- | --- |
| `.factory/blueprint.json` | This repo dogfooding itself: the blueprint for its own automation lines. |
| `.factory/prompts/*.md` | The prompt contract for each Claude agent machine. |
| `.factory/config.yml` | Compile-time configuration for this repo's factory. |
| `schema/blueprint.schema.json` | The blueprint contract. Drift-guarded against the machine registry. |
| `app/src/compiler/` | The compiler itself, plus its invariant tests. |
| `examples/*.json` | Example blueprints used as compiler fixtures. |

### Generated — never hand-edit these

| Path | Produced from |
| --- | --- |
| `.github/workflows/factory--*.yml` | `.factory/blueprint.json` + `.factory/prompts/` + `.factory/config.yml` |
| `examples/compiled/` | The example blueprints in `examples/` — reference output the compiler is expected to converge to. |

Every generated workflow carries a `GENERATED BY GITFACTORY` header. That header
is the marker the drift check and the human reviewer both key off.

> **Not everything in `.github/workflows/` is generated.** The hand-written
> CI, Pages, and evolve workflows live alongside the compiled `factory--*.yml`
> lines and are ordinary files you edit normally. The `factory--` prefix and the
> banner are what distinguish them.

## Checking your work

The compiler has invariant tests. From `app/`:

```bash
npm test          # vitest — compiler invariant tests
npm run typecheck # tsc --noEmit
npm run build     # typecheck + production build
```

If you are working inside Claude Code, the `/compile-check` slash command in
`.claude/commands/` wraps this loop.

## When the drift check fails

CI compares the committed generated files against what the compiler produces
from the committed source. A failure means those two disagree. In practice it is
almost always one of three things:

1. **You edited a generated file directly.** Revert the edit, make the
   equivalent change in `.factory/` (see the table above), regenerate.
2. **You changed source but didn't regenerate.** Run the regeneration command
   and commit the resulting diff.
3. **You changed the compiler or the schema.** The output *should* change — that
   is the point. Regenerate so the committed artifacts (including
   `examples/compiled/`) reflect the new behaviour, and make sure the diff is
   the change you intended. A compiler change with a surprisingly large output
   diff is a review signal, not a rubber stamp.

A drift failure is never fixed by editing the generated file to match, and never
by loosening the check.

## Reviewing a PR that touches generated files

- A generated-file diff with **no corresponding source diff** is a red flag —
  either a hand edit or a non-deterministic compiler.
- A source diff with **no generated diff** usually means the author forgot to
  regenerate; CI should already be red.
- Read the source change; skim the generated change for *shape*. The emitted
  YAML is meant to be readable precisely so this skim is possible.
