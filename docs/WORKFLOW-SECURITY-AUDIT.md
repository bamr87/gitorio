# Workflow security audit: triggers, checkout refs, permissions

> **STATUS: procedure only — findings not yet populated.**
>
> This document defines *how* to audit this repository's GitHub Actions
> workflows and *what* to record. The findings table in
> [Findings](#findings) is empty on purpose: it must be filled in by reading
> the actual files under `.github/workflows/`, not inferred. Do not guess a
> row. An unfilled row is honest; a wrong row is a false sense of safety.

## Why this exists

The note on local composite actions warns that combining the `pull_request_target` event with a checkout of pull-request *head* code is dangerous. That warning is generic. This audit exists to replace it with a concrete statement about this repository's actual exposure — one row per workflow, recording the events it triggers on, the ref it checks out, and the `permissions:` it declares.

## Scope

Every file under `.github/workflows/`. Per the repository README that directory contains two populations, and **both** are in scope:

- hand-written CI / Pages / evolve workflows, and
- the compiled `factory--*.yml` assembly lines, which carry a
  `GENERATED BY GITFACTORY` header and must never be hand-edited.

A finding in a generated file is a finding against the **compiler**, not the file. Fix it in `app/src/compiler/` (and in the blueprint or machine registry if the unsafe shape is expressible there), then recompile. Patching the YAML by hand will be overwritten on the next compile.

Reusable and composite actions invoked by these workflows (`uses: ./...`, `uses: owner/repo/.github/workflows/x.yml@ref`) are in scope for the *privileges they inherit*, because a called workflow or composite action runs with the caller's token and, in the composite case, against the caller's workspace.

## Background: what actually makes a workflow dangerous

Three properties have to line up. Any one alone is usually fine.

1. **A trigger that runs in the base repository's trust context.**
`pull_request_target`, `issue_comment`, `workflow_run`, `schedule`, and `push` all evaluate in the context of the *base* repository: the job gets the repository's `GITHUB_TOKEN` and can read repository secrets, even when the pull request came from a fork.

By contrast, `pull_request` from a fork runs with a read-only `GITHUB_TOKEN` and no access to repository secrets. That is the safe default and the reason `pull_request_target` exists at all — someone wanted a token or a secret.

2. **A checkout of attacker-controlled code.** For
`pull_request_target`, `actions/checkout` defaults to the *base* ref, which is safe. The hazard is an explicit override such as:

   ```yaml
   - uses: actions/checkout@v4
     with:
       ref: ${{ github.event.pull_request.head.sha }}
       # or: ${{ github.event.pull_request.head.ref }}
       # or, with a fork: repository: ${{ github.event.pull_request.head.repo.full_name }}
   ```

For `workflow_run`, the equivalent is downloading and unpacking an artifact produced by the untrusted run.

Note the asymmetry that trips people up: the *workflow file itself* is always read from the base branch under `pull_request_target`, so a pull request cannot edit the workflow to attack you. It can only supply the *code the workflow chooses to run*.

3. **Execution of that code.** Rarely an explicit `run: ./attacker-script`.
   Far more often it is implicit:

   - `npm install` / `npm ci` running `prepare`, `postinstall`, or other
     lifecycle scripts from the checked-out `package.json`;
   - a build, test, or lint step running checked-out config
     (`vite.config.ts`, `eslint.config.js`, `vitest` setup files) — all of
     which are executable code;
   - **`uses: ./path/to/action`**, which resolves against the *workspace*, so
     after a head checkout it runs the pull request's version of that
     composite action. This is the specific hazard the local-composite-actions
     note flags;
   - an agent step handed the diff or the working tree with write tools
     enabled.

When all three line up, an unreviewed pull request from any fork executes with the repository's token and secrets. With `contents: write` that is a supply chain compromise; with `secrets` in the environment it is credential theft.

### A fourth thing to record: `permissions:`

`permissions:` narrows the `GITHUB_TOKEN`. It can appear at workflow level, at job level (which *replaces*, not merges with, the workflow level), or not at all — in which case the token gets the repository or organisation default, which is a settings-page value, not something visible in the YAML. **Check that setting once and record it in the Findings preamble**, because every workflow with no `permissions:` block inherits it.

Record `permissions:` even for workflows that look safe. It is the blast radius if any of the other three properties changes later.

## Procedure

Run from the repository root. These are ordinary shell utilities, not project scripts.

```sh
# 1. Inventory.
ls .github/workflows/

# 2. Which files use a base-context trigger?
grep -rn -E 'pull_request_target|issue_comment|workflow_run' .github/workflows/

# 3. Which files override the checkout ref, or check out another repository?
grep -rn -A6 'actions/checkout' .github/workflows/

# 4. Which files declare permissions, and which rely on the repo default?
grep -rn -A8 'permissions:' .github/workflows/
grep -rLn 'permissions:' .github/workflows/*.yml   # files with none

# 5. Which files reference a local composite action?
grep -rn -E 'uses:\s*\./' .github/workflows/

# 6. Which files touch secrets?
grep -rn 'secrets\.' .github/workflows/
```

Then open each file that matched anything in steps 2–6 and read it. `grep` finds candidates; only reading finds the truth — in particular, whether the risky steps are gated behind a condition such as an author-association check, a label, or an environment with required reviewers.

## Fields to record

One row per workflow file.

| Field | What goes in it |
| --- | --- |
| **Workflow** | Filename, and whether it is hand-written or compiled (`factory--*.yml`). |
| **Events** | Every key under `on:`, with qualifiers (`types:`, `branches:`, `paths:`). |
| **Checkout ref** | `base` (the `pull_request_target` default), `default` (no checkout, or plain `actions/checkout` on a push/schedule), `PR head`, `artifact from another run`, or `n/a`. Include `repository:` if it is not this repo. |
| **`permissions:`** | The declared block, verbatim and abbreviated (e.g. `contents: read, issues: write`). Write `— (repo default)` if absent, and say what that default is in the preamble. |
| **Secrets** | Which `secrets.*` are referenced, especially model/API keys and any PAT. |
| **Untrusted code executed?** | Yes / No / Gated. "Gated" needs the gate named — e.g. "only when a maintainer applies the `safe-to-run` label". |
| **Risk** | Per the rubric below. |
| **Notes** | The gate, the mitigation, or the reason it is fine. |

## Risk rubric

| Level | Definition |
| --- | --- |
| **High** | Base-context trigger **and** checkout/execution of pull-request-controlled code **and** a write permission or a secret in scope. Fix before anything else. |
| **Medium** | Base-context trigger with write permissions or secrets, but no untrusted code executed — the exposure is one careless step away. Also: any workflow relying on a permissive repository default instead of an explicit `permissions:` block. |
| **Low** | `pull_request` only, read-only token, no secrets; or a base-context trigger whose untrusted path is gated behind an explicit maintainer action. |
| **None** | No untrusted input reaches the job at all (e.g. `schedule` over repository-owned content with a scoped token). |

## Safe patterns

When a row comes out High or Medium, these are the standard fixes, roughly in order of preference.

1. **Use `pull_request` instead.** If the job does not need a write token or a
secret, this removes the entire class of problem. Fork pull requests get a read-only token and no secrets.

2. **Split the workflow.** Untrusted build/test work runs under
`pull_request` with no privileges and publishes its output as an artifact. A separate privileged workflow consumes that artifact and treats every byte of it as data — never as code, never as a path, never interpolated into a shell command.

3. **Do not check out the head at all.** Under `pull_request_target`, leave
`actions/checkout` at its default (base ref). If you need PR *metadata*, read it from the event payload rather than the tree.

4. **Gate the privileged path.** Require a maintainer-applied label, an
`author_association` check, or a deployment `environment` with required reviewers before any step that touches head code. Record the gate in the Notes column so the next auditor does not have to rediscover it.

5. **Declare `permissions:` explicitly, at the narrowest scope.** Start from
`permissions: {}` or `contents: read` at workflow level and grant per-job only what that job needs. Remember that a job-level block replaces the workflow-level one wholesale.

6. **Never interpolate event text into `run:`.** Titles, bodies, branch names,
and comment text are attacker-controlled. `${{ github.event.* }}` inside a `run:` block is a shell injection. Pass values through `env:` and reference them as quoted shell variables.

7. **Pin third-party actions to a full commit SHA**, and prefer
   first-party or vendored actions on any workflow that holds a write token.

8. **For agent steps, keep the tool grant scoped and the loop bounded.** An
agent with write tools reading an untrusted diff is the same exposure as `run:` on untrusted code, just harder to see.

## Keeping this current

Re-run the audit when:

- a workflow is added, or its `on:` block changes;
- a `permissions:` block is added, removed, or widened;
- the compiler learns to emit a new trigger or a new checkout shape — a single
  compiler change edits every generated line at once;
- the repository's default `GITHUB_TOKEN` permission setting changes.

The durable version of this document is a CI gate rather than a table: a check that fails when a workflow combines a base-context trigger with a PR-head checkout without a recorded gate. Until that exists, this page is the record.
