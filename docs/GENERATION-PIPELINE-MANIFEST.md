# Rendering the generation-pipeline table from the manifest

> **Status: proposal / not yet implemented.** This document specifies a contract. It
> does not describe behaviour that exists today. Sections marked `<TBD>` depend on the
> generation manifest landing first (see [Prerequisites](#prerequisites)).

## The problem

The set of files the compiler writes is currently described in **two places that can
drift apart**:

1. the compiler itself, which knows what it emits; and
2. a hand-maintained prose table listing the generated paths.

Nothing forces (2) to follow (1). A machine gains an output, an emitter is renamed, a
`factory--*.yml` line is retired — and the table quietly becomes a lie. Because the
emitted workflows carry a `GENERATED BY GITFACTORY` header and are explicitly
never-hand-edit files (see [`GENERATED-FILES.md`](GENERATED-FILES.md)), a stale table is
worse than no table: it tells a contributor that a file is safe to edit when it is not,
or omits a file that will be clobbered on the next compile.

The fix is to make the prose table a **derived artifact**: render it from the manifest
the compiler already produces, and fail CI when the committed rendering differs from the
fresh one.

## Prerequisites

This work is deliberately **sequenced after** the manifest emitter. It cannot be bundled
into the emitter change, because rendering from a manifest requires the manifest to exist
*and* to be trusted as the single source of truth.

## Proposed manifest shape

The renderer needs, for each emitted file, enough to fill a row a human can act on. A
minimal sufficient entry:

```jsonc
{
  "paths": [
    {
      "path": ".github/workflows/factory--<line>.yml", // repo-relative destination
      "source": ".factory/blueprint.json",             // what it was compiled from
      "machine": "<machine id>",                       // which machine emitted it, if any
      "kind": "workflow"                               // workflow | prompt | config | ...
    }
  ]
}
```

These field names are a **proposal**, not a description of an existing file. Reconcile
them with the emitter implementation before writing the renderer; the renderer should
read the manifest's real schema rather than this document.

## Rendering contract

1. **One source of truth.** The renderer reads only the manifest. It must not walk the
   filesystem, glob `.github/workflows/factory--*.yml`, or hardcode any path. If a file
   is missing from the table, that is a manifest bug, and it should be fixed in the
   emitter.
2. **Marker-delimited region.** The generated table is written between explicit markers
   so the surrounding prose stays hand-authored:

   ```markdown
   <!-- BEGIN GENERATED: generation-pipeline-table -->
   | Path | Source | Machine |
   | --- | --- | --- |
   ...
   <!-- END GENERATED: generation-pipeline-table -->
   ```

   Everything outside the markers is owned by humans; everything inside is overwritten
   wholesale. This keeps the doc reviewable — a diff shows exactly which rows moved.
3. **Stable ordering.** Rows are sorted by `path` (byte order), so unrelated compiler
   changes do not shuffle the table and produce noisy diffs.
4. **Escaping.** Paths and machine ids are emitted as inline code spans; any `|` in a
   value must be escaped so it cannot break the table.
5. **Idempotence.** Running the renderer twice in a row produces a byte-identical file.

### Determinism

The rendered table must be a pure function of the manifest. No timestamps, no
"generated on", no run ids, no absolute paths, no locale-dependent sorting. This is the
same guarantee the compiled workflows are held to; without it the CI check below becomes
a flaky test rather than a drift guard.

## The CI check

The check re-renders the table and compares it against what is committed:

1. Read the manifest.
2. Render the table region.
3. Diff against the committed file.
4. **Fail** on any difference, printing the diff and the exact command to regenerate.

Failure message should name the fix, not just the problem — the contributor who trips
this is usually someone who added a machine output and has no idea this doc exists.

## Out of scope

- **Changing what the compiler emits.** This is a documentation pipeline; it reports on
  the emitter, it does not extend it.
- **The README's repository-layout table.** That table describes authored directories,
  not generated files, and has a different source of truth. It is a separate drift
  problem.
- **`_docs/`.** Per [`DOCUMENTATION-MAP.md`](DOCUMENTATION-MAP.md), `_docs/` is the
  user-facing collection rendered in the app; this note is a contributor-facing design
  doc and stays in `docs/`.
