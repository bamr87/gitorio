# Determinism contract for compiled output

> **Audience:** anyone changing the compiler in `app/src/compiler/`, adding a
> machine, or teaching an emitter a new trick.
> **Read this before you write the emitter, not after CI turns red.**

Related: [`GENERATED-FILES.md`](GENERATED-FILES.md) (which files are generated, how to regenerate them, action pinning) · [`ARCHITECTURE.md`](ARCHITECTURE.md) (compiler spec).

## The guarantee

> Compiling the same blueprint twice produces **byte-identical** output — on any
> machine, on any operating system, at any time, in any order.

Formally: the compiler is a pure function `compile(blueprint) -> files`. The only input is the blueprint (plus repo configuration that is itself checked in). No clock, no network, no filesystem layout, no environment variables, no randomness.

## Why this is load-bearing

The compiler's output is **committed to the repository**, not produced at run time. The generated GitHub Actions workflows live in `.github/workflows/` as `factory--*.yml` files carrying a `GENERATED BY GITFACTORY` header, and `examples/compiled/` holds reference output that the compiler is expected to converge to.

That arrangement buys a lot — the emitted YAML is readable, reviewable in a diff, and keeps working even if GitFactory disappears — but it only holds if output is reproducible:

- **Diffs stay meaningful.** If recompiling an unchanged blueprint rewrites a
timestamp or reshuffles job order, every unrelated PR carries noise and real changes hide inside it.
- **The reference output stays a target.** `examples/compiled/` can only be
  compared against if there is one right answer.
- **Drift checks stay honest.** A check that flaps for non-semantic reasons gets
  muted, and then it is protecting nothing.
- **Review stays possible.** "The workflow changed because the blueprint changed"
  is a claim a reviewer can check. "The workflow changed" is not.

Each rule below exists because breaking it silently breaks one of those four.

## The rules

### 1. No wall-clock values

Nothing that depends on *when* the compile ran may reach the output: no timestamps, no dates, no elapsed times, no "generated on …" comments, no year in a header. Not in YAML values, not in comments, not inside an id.

If output needs provenance, use something derived from the input — a blueprint content hash, a version string that is checked in — rather than the clock. Git already records when a file changed; the file should not duplicate that badly.

### 2. No ambient environment

The compile must not observe the machine it runs on:

- no `process.env` reads that reach the output,
- no absolute paths, home directories, hostnames, or usernames,
- no locale-dependent formatting (`toLocaleString`, locale-aware `sort`,
locale-aware number/date formatting) — use explicit, locale-independent formatting and comparison,
- no OS-dependent path separators — see rule 4,
- no randomness: `Math.random`, `crypto.randomUUID`, or anything seeded from the
  clock or the process id.

### 3. Sort before iterating any map

Object key order, `Map` order, and `Set` order encode *authoring history* — the order nodes happened to be added to the canvas, the order a JSON parser saw keys. That history is not part of the blueprint's meaning, and it changes when a user drags a machine around.

So: before emitting anything derived from a collection, sort it by a stable, content-derived key (usually the node or machine id) with an explicit comparator. This applies to jobs, steps, `needs:` lists, permission blocks, env blocks, tool grants, matrix entries — anything that ends up as a sequence or as a set of keys in the emitted YAML.

When order *is* semantic (belt order determines step order), the order must come from the blueprint graph, not from iteration order over a container.

### 4. Repo-relative paths only

Every path in the output is relative to the repository root and uses forward slashes — `.factory/prompts/triage.md`, never `/Users/…/.factory/prompts/triage.md` and never a backslash-separated path. Build paths by joining known-relative segments; do not derive them from the compiler's own location on disk.

### 5. Derive ids from content, not from counters

Any identifier the compiler invents — job names, step ids, anchors, cache keys, blueprint fingerprints — must be a pure function of the blueprint content.

A counter (`step-1`, `step-2`) is only safe if the sequence it counts is itself fully determined by the blueprint *and* stable under unrelated edits. It usually is not: inserting a machine renumbers everything after it, producing a large diff for a small change. Prefer a hash of the node's content, or the node's own id.

If you do hash: hash a canonical serialisation (keys sorted, no whitespace variance), so that the hash does not depend on the very ordering rule 3 exists to eliminate.

### 6. Pin external references

Third-party actions referenced by emitted workflows are pinned, so that the meaning of a generated workflow does not drift underneath a repository that never changed. See [`GENERATED-FILES.md`](GENERATED-FILES.md) for the pinning format this project uses and for how pins are updated.

A floating reference (`@main`, `@v4` where the tag moves) is not a determinism violation in the byte sense — the emitted file is stable — but it breaks the same promise one level down: the same file no longer means the same thing.

### 7. The bytes, not just the structure

Two YAML documents that parse equal are still a diff if they are not equal as text. So the emitter also owns:

- consistent indentation and quoting style,
- consistent line endings (see `.gitattributes` / `.editorconfig`),
- exactly one trailing newline,
- no trailing whitespace,
- stable key order within each emitted mapping (sorted, or a fixed canonical
  order — but the same one every time).

## Checklist for an emitter change

Before you open the PR:

- [ ] No `Date`, `Date.now`, `performance.now`, `Math.random`, `crypto.randomUUID`,
      or `process.env` on any path that reaches output.
- [ ] Every iteration over an object, `Map`, or `Set` that produces output is
      preceded by an explicit sort with an explicit comparator.
- [ ] Every emitted path is repo-relative and forward-slashed.
- [ ] Every generated id is a function of blueprint content.
- [ ] New external action references are pinned per
      [`GENERATED-FILES.md`](GENERATED-FILES.md).
- [ ] Compiled twice locally and diffed the results — no change.
- [ ] Regenerated the checked-in output (`.github/workflows/factory--*.yml`,
      `examples/compiled/`) and committed it in the same PR, so the diff shows
      what your change does to real output.
- [ ] `cd app && npm test` passes (the vitest suite includes compiler invariant
      tests).

A reviewer should be able to answer "would this produce different bytes on my machine tomorrow?" from the diff alone. If they cannot, the change needs a comment explaining why not.

## How the contract is enforced

Three things guard it today:

1. **Compiler invariant tests** — `cd app && npm test` (vitest). This is where a
new rule should grow a test: prefer a test that compiles a fixture twice and asserts byte equality over a test that asserts one specific string.
2. **Reference output** — `examples/compiled/` holds output the compiler is
expected to converge to; a drift means either the emitter changed behaviour or the reference needs regenerating, and the PR must say which.
3. **Schema drift guard** — `schema/blueprint.schema.json` is kept in step with
the machine registry, so a new machine cannot quietly widen the input surface without the contract being reconsidered.

None of these can catch a violation that only shows up on someone else's machine — a locale-dependent sort, an environment read — which is why the rules above are stated as rules rather than left to CI.

## When you genuinely need non-reproducible data

Sometimes the *deployed* workflow legitimately needs a value that cannot be known at compile time: the run id, the triggering actor, the current date for a nightly report. That is fine — the distinction is **compile time vs. run time**.

- Emit a *reference* to the value (a GitHub Actions expression, a step that
computes it at run time), not the value itself. The reference is a constant; the value is not.
- If a value must be chosen at compile time and is not derivable from the
blueprint, it belongs in the blueprint or in checked-in configuration — pass it in as an explicit input rather than reading it from the ambient world.

If neither is possible, the change needs a decision record ([`DECISIONS.md`](DECISIONS.md)) rather than a quiet exception, because it makes the committed output unreviewable.
