# GitHub Actions supply-chain policy

**Status:** authored contributor doc. Canonical home for the pinning, allowlist, and Dependabot rules that were previously only visible as scattered TODO comments.

Every workflow in this repository runs with credentials on a repository that hosts agents which can open PRs and comment on issues. A third-party action is code we execute in that context. This page states the rules once so a reviewer can cite them in a PR instead of relying on memory.

**Scope:** everything under `.github/workflows/` — hand-written CI/Pages/evolve workflows *and* the compiled `factory--*.yml` lines — plus any composite action or reusable workflow this repo defines.

---

## 1. Pinning

> **Rule.** Third-party actions are pinned to a full 40-character commit SHA with a
> trailing comment naming the human-readable version. GitHub-owned actions
> (`actions/*`, `github/*`) may use a major version tag.

```yaml
# Third-party — required form:
- uses: owner/action@1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b  # v1.2.3

# GitHub-owned — major tag is fine:
- uses: actions/checkout@v4
```

Not acceptable for a third-party action:

```yaml
- uses: owner/action@v1          # a tag is mutable; upstream can repoint it
- uses: owner/action@main        # a branch is mutable by definition
- uses: owner/action@1a2b3c4d    # short SHAs are not collision-proof
- uses: owner/action@1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b   # no version comment
```

**Why a SHA.** Git tags are mutable. An upstream maintainer — or anyone who compromises that account — can move `v1` to point at new code, and every workflow referencing `@v1` picks it up on the next run with no diff in this repository. A commit SHA is content-addressed: it cannot be repointed.

**Why the trailing comment.** A bare SHA is unreadable and unreviewable. The `# v1.2.3` comment is what lets a reviewer see at a glance which release is pinned, and what lets a bump PR be read as "v1.2.3 → v1.3.0" rather than "forty hex characters changed".

**Why GitHub-owned actions are exempt.** `actions/*` and `github/*` are published by the same party that runs the runner and holds the credentials. Pinning them to a SHA buys nothing against a threat model in which GitHub itself is trusted, and costs readability plus a stream of Dependabot noise. If that trust assumption ever changes, change it here first.

### 1.1 Compiled workflows are a special case

`.github/workflows/factory--*.yml` are **generated** — they carry a `GENERATED BY GITFACTORY` header and are produced by the compiler from `.factory/blueprint.json`. See [`GENERATED-FILES.md`](GENERATED-FILES.md).

A bad or missing pin in a generated workflow is a **compiler bug, not a YAML bug**. Editing the emitted file in place is reverted by the next compile. Fix the action reference at its source in the compiler / machine registry under `app/src/compiler/`, re-compile, and commit the regenerated workflow. The same applies to a Dependabot bump that lands on a generated file: port the new SHA into the compiler and let the file be regenerated, rather than merging the bump as-is.

## 2. The allowlist

> **Rule.** The set of third-party actions used in this repository is deliberately
> small and closed. Adding one is a reviewed decision, not an implementation detail
> of the PR that needs it.

This page does not enumerate the current entries, because the authoritative list is the set of `uses:` lines actually present in `.github/workflows/` — a hand-copied list here would drift. To see it:

```bash
grep -rhoE '^\s*-?\s*uses:\s*\S+' .github/workflows/ | sort -u
```

> **Unverified:** the enforcement mechanism (repository/org *Settings → Actions →
> General → Allow specified actions*, a gate under `tools/`, or convention alone) is
> not recorded here yet. Whoever knows should name it in this section — the rule is
> the same however it is enforced today.

**Criteria for adding a third-party action.** All of them, in the PR that introduces it:

1. **It earns its place.** Three lines of `run:` shell beat a dependency that runs
   arbitrary code with the job's token. Prefer the shell.
2. **It is pinned per §1**, with the version comment.
3. **The publisher is identifiable and the repo is alive** — a real maintainer or org,
   recent commits, a tagged release history.
4. **The permissions it needs are stated** in the job's `permissions:` block, narrowed
   to the minimum. Default to read-only and add scopes explicitly.
5. **The PR body says why**, in one sentence a future reviewer can weigh.

Removing an action needs no ceremony. Fewer is better.

## 3. Dependabot keeps the pins fresh

A SHA pin is a snapshot. Without something to advance it, "pinned" quietly becomes "stuck on a version with a known CVE" — the pin trades an unbounded-trust problem for a staleness problem, and Dependabot is how that trade is paid off.

> **Rule.** The `github-actions` ecosystem entry in `.github/dependabot.yml` is the
> mechanism that advances these pins. It is part of this policy, not an optional
> convenience: **do not remove it, and do not disable it to quiet the noise.** If the
> noise is the problem, reduce the number of third-party actions (§2).

Dependabot understands SHA-pinned actions: it opens PRs that move the SHA *and* update the trailing version comment, which is another reason §1 requires that comment.

> **Unverified:** the entry's exact `directory`, `schedule.interval`, and grouping
> config are not restated here. Read `.github/dependabot.yml` for the current values;
> if there is no `github-actions` entry, adding one is the fix.

### Reviewing a Dependabot Actions bump

These PRs are routine, which is exactly why they are worth a real look:

- **Does the new SHA belong to the release the comment claims?** Open the upstream
repo at that tag and confirm the commit matches. This is the check that catches a compromised or repointed release.
- **Read the upstream changelog** for new permission requirements, new network calls,
  or a new sub-dependency.
- **Major version bumps get real review**, not a merge queue. Breaking changes in an
  action can silently change what a workflow is authorised to do.
- **If the file is generated**, apply §1.1 — port the SHA into the compiler instead.

## 4. Reviewer checklist

For any PR touching `.github/workflows/`:

- [ ] Every new `uses:` referencing a non-`actions/`, non-`github/` action is a full
      40-character SHA with a `# vX.Y.Z` comment (§1).
- [ ] Any newly introduced third-party action meets all five criteria in §2, and the
      PR body says why it is needed.
- [ ] The job's `permissions:` block is present and minimal.
- [ ] No edits to a `GENERATED BY GITFACTORY` file that should have been made in the
      compiler (§1.1).

> **Open item:** the existing pin-check TODO should point at this page and, once an
> automated gate exists, be deleted. Its file/line reference has not been filled in
> here — see the follow-up issue.

Until a gate exists, this checklist is the enforcement. Reviewers may cite this page by link when requesting changes.
